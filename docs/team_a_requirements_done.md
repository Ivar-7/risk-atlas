# Team A PDF requirements completed

Source: [Nairobi Urban Flood Challenge — Team A problem statement](../data/Team_A_Nairobi_Problem_Statement%20%281%29.pdf), especially sections 2, 5, 7, 9, and 11. This checklist covers the required prototype and deliverables; the PDF's suggested technologies and stretch ideas are not requirements.

| PDF requirement | Completed work and evidence |
| --- | --- |
| **Ingest Nairobi flood hazard data.** | The model reads the starter kit's five 0–1 pluvial susceptibility tiers with the 600-building synthetic exposure and uses the supplied GeoTIFFs for added locations. The values are labelled as a constructed proxy, not observed depth. [Ingestion](../server/app/engine/ingestion.py) · [Hazard lookup](../server/app/engine/hazard_validation.py) · [Assumptions](assumptions.md) |
| **Explain how proxy severity becomes damage input.** | A positive score activates the fixed damage ratio for the source tier and building class; zero gives zero damage. No measured or inferred flood depth enters the loss engine. The five tiers and assumed return periods are documented. [Model parameters](../config/model_parameters.yaml) · [Assumptions](assumptions.md) |
| **Apply a sourced vulnerability reference for building types.** | The JRC Africa residential depth-damage table is documented as a reference. The live model uses explicitly assumed fixed ratios for four construction classes across the five source tiers, as requested in Step 2. Portfolio analysis shows a four-class line graph through the five matrix points, with the exact table in Construction; the lines are visual connectors, not continuous loss functions. The ratios are not JRC class-specific values or locally calibrated claims curves. [Vulnerability graph](../client/src/components/ui/dashboard-4-utils/vulnerability-chart.tsx) · [Vulnerability engine](../server/app/engine/vulnerability.py) · [Model parameters](../config/model_parameters.yaml) · [Assumptions](assumptions.md) |
| **Run a synthetic exposure portfolio.** | The 600 starter buildings have locations, construction classes, insured values, and tier scores. Imported rows are validated; reviewed free-text additions are marked synthetic. [Exposure data](../data/exposure_nairobi_with_hazard.csv) · [Ingestion](../server/app/engine/ingestion.py) · [Portfolio runner](../client/src/features/model/CatModelRunner.tsx) |
| **Calculate and aggregate property losses across flood tiers.** | For each building and tier, the pipeline combines hazard, vulnerability, and TIV, then sums ground-up and gross insured losses for the portfolio and construction classes. [Pipeline](../server/app/engine/pipeline.py) · [Financial engine](../server/app/engine/financial.py) |
| **Show financial terms and a return-period/EP curve.** | The portfolio model applies assumed per-property deductibles and limits, sums ground-up and gross insured loss, then applies portfolio quota share and an optional aggregate cat XOL layer to each scenario. Portfolio analysis shows the financial waterfall, gross and net AAL, and 1-in-100/250 values; Scenario detail shows gross and net EP curves and the recovery table. The document workspace retains its separate single-occurrence terms and waterfall. Treaty reinstatements, annual aggregates and verified contract wording are not modelled. [Loss curve](../client/src/components/ui/dashboard-4-utils/revenue-chart.tsx) · [Portfolio financial engine](../server/app/engine/financial.py) · [Assumptions](assumptions.md) |
| **Use AI to materially change the result and show its contribution.** | A saved, reviewed `gpt-6-luna` extraction of 25 Kibera buildings was replayed under model v1.3.0. It adds KES 20,000,000 TIV and increases the illustrative 1-in-100 gross insured loss by KES 5,400,000 versus the same portfolio without those rows. The current run records the reviewed groups, model, response ID, and before/after losses. [Current replay evidence](current_ai_replay_evidence.json) · [Original live-demo evidence](live_ai_demo_evidence.json) · [AI demo instructions](ai_exposure_demo.md) · [AI evidence view](../client/src/components/ui/dashboard-4-utils/ai-evidence.tsx) |
| **Provide a clear results interface.** | The dashboard shows total exposure, key return-period losses, the EP curve, construction-class breakdown, map, AI output and comparison, and assumptions. [Dashboard](../client/src/components/ui/dashboard-4.tsx) · [Workspace](../client/src/pages/DashboardPage.tsx) |
| **Identify data provenance, assumptions, and limits.** | The interface and written notes identify the portfolio as synthetic, the hazard as a proxy, fixed vulnerability ratios and return periods as assumptions, and the drainage uplift as an unvalidated sensitivity. The common proxy flags 12 of 24 geocoded hotspot centres; no claim of measured pluvial depth or local claims calibration is made. [Assumptions register](../config/assumptions_register.yaml) · [Assumptions](assumptions.md) · [Submission note](submission_note.md) |
| **Submit a working demo and short note on sources, assumptions, and AI.** | The portfolio runner and dashboard form the demo; the written note covers all three requested topics. The live AI extraction and local reviewed API run are captured separately. [Submission note](submission_note.md) · [Live evidence](live_ai_demo_evidence.json) · [API guide](api.md) |

The EP frequencies, five-tier damage ratios, and policy terms are prototype assumptions. The EP chart contains five assumed points through 1-in-250; it has no 10,000-year event simulation, bootstrapped uncertainty band, or 1-in-500 estimate. The original live-demo file records a separate local run under the previous vulnerability method with database persistence mocked. The current evidence file records a persisted v1.3.0 replay of another saved, reviewed live AI extraction; the replay reused its recorded groups and did not call the AI service again.
